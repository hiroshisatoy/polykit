# PolyKit システム設計

## 1. 文書の目的

本書は、PolyKit のシステム全体の構成と設計判断を定義する。

対象読者は、プロジェクトの経緯を知らない開発者、レビュー担当者、
およびリリース担当者である。
本書を起点に、機能の配置、実行順序、状態管理、外部依存、
テスト範囲を判断できることを目標とする。

ポップアップ固有の詳細仕様は
[ポップアップと画面翻訳設定の設計](popup-and-interface-translation-design.md)
で定義する。

## 2. プロダクトの目的

PolyKit は、WordPress.org の翻訳プラットフォームである
`translate.wordpress.org` 上の日本語翻訳作業を支援する
ブラウザー拡張機能である。

GlotPress が提供する翻訳画面を置き換えず、既存画面へ次の機能を追加する。

- 日本語翻訳ルールに基づく自動チェック
- 用語集と既存訳の確認
- Approve、Reject、Fuzzy などのレビュー操作の効率化
- 複数文字列に対する一括操作
- 文字数、語数、メタ情報、補助リンクの表示
- GlotPress 画面と PolyKit 独自 UI の日本語化
- 利用者ごとの設定とチェック重要度の保存

PolyKit は GlotDict 由来のコードを含むが、日本語翻訳ワークフローに特化した
独立した拡張機能として設計する。

## 3. 設計目標

### 3.1 既存サイトとの共存

GlotPress の画面構造と公開 JavaScript オブジェクトを利用し、
サーバー側コードを変更せずに機能を追加する。
既存のフォーム送信、編集、レビュー権限を迂回しない。

### 3.2 日本語ルールの分離

言語非依存の検証と日本語固有の検証を別の処理として管理する。
日本語ルールの変更が、プレースホルダーや HTML タグなどの一般検証へ
影響しない構造を保つ。

### 3.3 段階的な機能低下

翻訳辞書、変更履歴、用語集などの補助データを取得できない場合も、
主要なページ拡張と翻訳編集を継続できるようにする。

### 3.4 最小権限

コンテンツスクリプトの実行対象を `translate.wordpress.org` に限定する。
外部入力からコードを生成または実行せず、DOM へ追加する文字列は
テキストとして扱うか許可済みの要素だけに制限する。

### 3.5 ブラウザー間の共通実装

機能コードは Chrome と Firefox で共有する。
Manifest のバックグラウンド定義だけをパッケージ生成時に変換する。

## 4. 対象範囲

### 4.1 対象サイト

通常の機能対象は次の URL である。

```text
https://translate.wordpress.org/*
```

WordPress Playground のページは DOM と実行環境が異なるため対象外とする。

```text
https://translate.wordpress.org/*/playground
https://translate.wordpress.org/*/playground/*
```

`manifest.json` のパターンは HTTP も含むが、機能内で生成するリンクと
ポップアップから操作するタブの判定は HTTPS に限定する。

### 4.2 対象外

- WordPress.org の認証や権限管理
- GlotPress サーバー API の提供または変更
- 翻訳内容の自動生成
- 複数端末間の設定同期
- GlotDict との同時利用

GlotDict と同時に利用すると、同一 DOM への追加処理やイベント登録が重複する。
そのため併用はサポートしない。

## 5. 実行コンテキスト

PolyKit は三つの実行コンテキストから構成される。

| コンテキスト | 主なファイル | 責務 |
| --- | --- | --- |
| 拡張機能バックグラウンド | `js/background.js` | インストール情報とタブ操作 |
| 拡張機能 UI | `popup.html`、`js/popup.js` | 共有設定と設定画面への導線 |
| 対象ページ | `js/init.js` と `js/polykit-*.js` | GlotPress の画面拡張と検証 |

### 5.1 拡張機能バックグラウンド

Chrome では Manifest V3 のサービスワーカーとして実行する。
サービスワーカーは停止と再起動が発生するため、実行中だけ必要な状態を
グローバル変数に保持しない。

インストールと更新の情報は `chrome.storage.session` に保存する。
ポップアップから設定画面を開く要求を受けた場合は、現在のタブへ
メッセージを送るか、新しい対象タブを作成する。

### 5.2 拡張機能 UI

ツールバーアイコンから独立したポップアップ文書を開く。
ポップアップは `chrome.storage.local` と Tabs API を利用するが、
対象ページの DOM へ直接アクセスしない。

### 5.3 コンテンツスクリプトとページスクリプト

`js/init.js` は Manifest からコンテンツスクリプトとして読み込まれる。
コンテンツスクリプトは次の境界処理を担当する。

- 拡張機能 API の利用
- 拡張機能内 JSON ファイルの取得
- ページへ渡す JSON データの公開
- ページコンテキストで動作するスクリプトの順序付き読み込み
- ポップアップとページスクリプト間のメッセージ中継

残りの `js/polykit-*.js` は script 要素としてページへ読み込まれ、
GlotPress の `$gp`、`$gp_editor_options`、jQuery、DOM にアクセスする。
これらは ES Modules ではなく、一つの共有グローバル名前空間で動作する。

## 6. 起動設計

### 6.1 起動順序

対象ページでは次の順序で起動する。

1. ブラウザーが `js/init.js` と基本 CSS を読み込む
2. 共有設定をページ側 `localStorage` へ反映する
3. PolyKit 独自 UI 用辞書の読み込みを開始する
4. GlotPress 画面翻訳辞書の読み込みを並行して開始する
5. JSON データを `#polykit-i18n-data` へ公開する
6. `jsScripts` の順序に従ってページスクリプトを読み込む
7. PolyKit の画面拡張を初期化する
8. GlotPress 辞書の準備後にデータを更新する
9. `polykit:gp-strings-ready` イベントで画面翻訳を開始する

変更履歴と GlotPress 辞書の取得は、主要スクリプトの起動を妨げない。

### 6.2 スクリプトの依存順序

`js/init.js` の `jsScripts` は依存順を表す。
配列の順序を変更するときは、参照する関数やグローバル値が先に定義されることを
確認する。

主要な層は次の順序になる。

1. 外部ライブラリ
2. 共通関数と i18n
3. 設定と入力機能
4. 検証と日本語ルール
5. 表示、メタ情報、一括操作、検索、整合性確認
6. 全体初期化

すべての動的読み込み対象は `manifest.json` の
`web_accessible_resources` に含める。

### 6.3 初期化失敗

ページスクリプトの読み込みに失敗した場合は、後続の初期化を中止する。
翻訳辞書または変更履歴だけが失敗した場合は、取得結果を空として継続する。

## 7. 機能コンポーネント

### 7.1 基盤

| ファイル | 責務 |
| --- | --- |
| `js/polykit-functions.js` | 共通 DOM、文字列、URL、イベント補助関数 |
| `js/polykit-i18n.js` | PolyKit 独自 UI の辞書初期化と文字列取得 |
| `js/polykit-settings.js` | 利用者判定、設定画面、設定値、重要度 |
| `js/polykit.js` | ページ種別を判定し、各機能を統合して起動する |

`js/polykit.js` は最終オーケストレーターであり、個別機能の詳細ロジックを
持たせない。

### 7.2 検証

| ファイル | 責務 |
| --- | --- |
| `js/polykit-validation.js` | レビュー実行と結果集約 |
| `js/polykit-checks.js` | プレースホルダー、空白、タグなどの一般チェック |
| `js/polykit-locale-validation.js` | 日本語固有の表記、用語、句読点チェック |

各チェック結果は `warning`、`notice`、`off` の三段階で扱う。

- `warning` は修正を強く促す問題である
- `notice` は確認を促すが、保存を妨げない情報である
- `off` はチェックを実行しない

一般チェックと日本語チェックは、可能な範囲で DOM に依存しない収集関数へ
分離する。
DOM へのラベル追加、ハイライト、保存制御は収集結果を受け取る側で行う。

### 7.3 翻訳作業の補助

| ファイル | 責務 |
| --- | --- |
| `js/polykit-consistency.js` | 既存訳候補とクイックリンク |
| `js/polykit-bulk-consistency.js` | 複数候補への置換と保存・却下 |
| `js/polykit-bulk.js` | 原文からの一括コピー |
| `js/polykit-column.js` | 行単位の Approve、Reject、Fuzzy 操作 |
| `js/polykit-meta.js` | 文字数、語数、複数形、日付情報 |
| `js/polykit-search.js` | 他プロジェクト検索と外部翻訳導線 |
| `js/polykit-notices.js` | 選択数と処理件数の通知 |

これらの処理は、GlotPress の既存編集行と `$gp.editor` を正本として扱う。
独自の翻訳状態モデルを別に保持しない。

一括処理は無制限に実行せず、安全上限と再試行上限を設ける。
対象行を確認してから変更し、タイムアウト時は処理を打ち切る。

### 7.4 GlotPress 画面の日本語化

`js/polykit-gp-l10n.js` は、`languages/ja/glotpress.json` の英日対応を使い、
既存 DOM のテキストノードと表示属性を翻訳する。

次の領域は翻訳対象外とする。

- 原文と訳文
- テキスト入力欄
- 用語集本体
- 翻訳候補の原文・訳文
- PolyKit 自身の設定と通知
- スクリプト、スタイル、コード

長い文字列を先に照合し、短い文字列による部分置換の競合を防ぐ。
HTML の整形による空白や改行の違いは同一の空白列として扱う。
動的に追加される DOM は MutationObserver で処理する。

### 7.5 PolyKit 独自 UI の日本語化

`languages/ja/polykit.json` は、PolyKit が追加するラベル、設定説明、通知を定義する。
ページスクリプトは文字列を直接取得せず、`polykit_t()` を使用する。

辞書キーが存在しない場合はキー自体を表示し、機能の初期化を継続する。
置換引数は `%s` と `%d` を出現順に置き換える。

## 8. 状態と永続化

### 8.1 保存領域

| 保存領域 | 用途 | 有効期間 |
| --- | --- | --- |
| `chrome.storage.session` | インストール・更新情報 | ブラウザーセッション |
| `chrome.storage.local` | 拡張機能 UI と共有する設定 | 拡張機能の削除まで |
| ページ `localStorage` | ページスクリプト設定と作業補助状態 | オリジン単位 |
| DOM | 辞書データと一時的な UI 状態 | ページ読み込み中 |

画面翻訳設定は `chrome.storage.local` を正本とし、ページ起動時に
同名の `localStorage` キーへミラーする。
その他の既存設定は `polykit_` 接頭辞のページ `localStorage` に保存する。

### 8.2 設定の既定値

設定の既定値は `js/polykit-settings.js` に集約する。
真偽値の一般設定と三段階のチェック重要度を別のマップで管理する。

既存の反転形式の設定キーは、読み込み時に現在の重要度形式へ正規化する。
保存値が破損している場合は例外を発生させず既定値へ戻す。

### 8.3 DOM を介したデータ受け渡し

コンテンツスクリプトとページスクリプトは JavaScript のグローバル空間を共有しない。
辞書データは実行不能な `application/json` の script 要素へ JSON として格納する。

```text
#polykit-i18n-data
```

ページ側は要素の `textContent` を JSON として解析する。
コード文字列として評価しない。

## 9. イベントとメッセージ

### 9.1 拡張機能メッセージ

| メッセージ | 送信元 | 受信先 | 目的 |
| --- | --- | --- | --- |
| `polykit-status` | `js/init.js` | バックグラウンド | インストール・更新情報の取得 |
| `polykit-open-settings-from-popup` | ポップアップ | バックグラウンド | 設定画面を開く |
| `polykit-open-settings` | バックグラウンド | `js/init.js` | 現在のページで設定を開く |
| `polykit-get-translate-interface` | ポップアップ | `js/init.js` | ページ側ミラー値の取得 |
| `polykit-set-translate-interface` | ポップアップ | `js/init.js` | 画面翻訳設定の変更 |

オブジェクト形式のメッセージは型を検証する。
対象外のメッセージは副作用なく無視する。

### 9.2 DOM カスタムイベント

| イベント | 目的 |
| --- | --- |
| `polykit:open-settings` | 初期化済みページへ設定画面表示を要求する |
| `polykit:gp-strings-ready` | GlotPress 辞書の準備完了を通知する |

設定画面要求はデータ属性にも保持し、ページスクリプトの初期化前に
イベントを受信しても失われないようにする。

## 10. 外部データと通信

PolyKit は、拡張機能内の辞書ファイルに加えて、対象サイト上の用語集や
Consistency 情報を取得する。

外部通信は現在の WordPress.org セッションと権限に従う。
取得結果を信頼済み HTML として直接挿入せず、必要な値だけを抽出する。

新しい外部通信を追加する場合は次を満たす。

- 利用目的を機能単位で限定する
- URL の動的部分をエンコードする
- HTTP エラーとネットワークエラーを処理する
- 失敗しても編集内容を破壊しない
- 認証情報や翻訳内容を第三者サービスへ暗黙に送らない

## 11. DOM 変更方針

### 11.1 冪等性

初期化関数は、同じページで複数回呼ばれても同一要素を重複追加しないようにする。
追加前に ID、クラス、対象列、既存ボタンの有無を確認する。

### 11.2 動的編集行

GlotPress は編集行を動的に表示または追加する。
初期 DOM だけを対象にせず、編集行追加フックまたは委譲イベントを利用する。

### 11.3 既存イベントとの統合

保存やレビュー操作は、可能な限り GlotPress の既存ボタンとイベントを発火して行う。
サーバー側 API を模倣する独自送信処理を増やさない。

### 11.4 安全な HTML

通常のラベルと通知には `textContent` と DOM API を使用する。
装飾目的で HTML を扱う必要がある場合は、`b` と `i` だけを許可し、
その他の要素はテキストまたは子要素へ変換する。

外部リンクを新しいタブで開く場合は `noopener` と `noreferrer` を設定する。

## 12. 権限とセキュリティ

| Manifest 項目 | 目的 |
| --- | --- |
| `storage` | セッション情報と共有設定の保存 |
| `activeTab` | ポップアップ操作時の対象タブ判定 |
| `host_permissions` | 対象サイトでの動作 |
| `web_accessible_resources` | ページコンテキスト用コードと辞書の読み込み |

次の制約を維持する。

- 対象サイト以外へコンテンツスクリプトを広げない
- `eval()` や動的コード生成を使用しない
- メッセージ入力の型と値を検証する
- 翻訳テキストをログや第三者サイトへ送信しない
- ユーザーの WordPress.org 権限を越える操作を実装しない
- Manifest 権限を追加するときは必要性とテストを同時に追加する

## 13. スタイル設計

ページ内 UI は PolyKit 用のクラスと CSS カスタムプロパティを使用し、
GlotPress の一般クラスへの広範な上書きを避ける。

| ファイル | 対象 |
| --- | --- |
| `css/common.css` | 共通トークンとページ全体の補助 UI |
| `css/translation.css` | 翻訳テーブルと編集行 |
| `css/settings.css` | ページ内設定パネル |
| `css/wp-plugins.css` | プラグイン翻訳ページ固有の表示 |
| `css/popup.css` | 拡張機能ポップアップ |

操作要素にはキーボードフォーカスを表示する。
状態は色だけに依存せず、テキスト、ラベル、形状のいずれかを併用する。
ポップアップは OS の配色設定に追従する。

## 14. ブラウザーと配布

### 14.1 Chrome

リポジトリの `manifest.json` をそのまま使用する。
バックグラウンドは `background.service_worker` として登録する。

### 14.2 Firefox

`pack-ext.js` がパッケージ内の Manifest だけを変換する。

- `background.service_worker` を `background.scripts` へ変換する
- Gecko 用の拡張機能 ID を追加する
- 作業ツリーの `manifest.json` は変更しない

### 14.3 パッケージ

次のコマンドで Chrome 用 ZIP と Firefox 用 XPI を生成する。

```sh
deno task pack
```

テスト、開発用設定、既存パッケージ、リポジトリ管理ファイルは成果物から除外する。

## 15. テスト設計

テストランナーには Deno を使用する。

```sh
deno task test
```

### 15.1 静的構成テスト

- Manifest が参照するファイルの存在
- 動的読み込みスクリプトの Web Accessible Resources 登録
- Chrome Manifest V3 の互換性
- Playground の除外
- パッケージ生成時の Firefox 差分

### 15.2 単体テスト

DOM から分離できる関数は、VM コンテキストまたは最小の DOM スタブで検証する。

- JSON と文字列処理
- URL 生成
- プレースホルダー検証
- 日本語固有の表記ルール
- GlotPress UI 文字列の置換
- 設定の既定値と重要度

### 15.3 統合に近いテスト

ブラウザー API と GlotPress オブジェクトをスタブ化し、次を検証する。

- ポップアップから設定画面を開く分岐
- バックグラウンドメッセージとフォールバック
- 動的編集行へのイベント登録
- 一括処理の上限、再試行、タイムアウト
- 翻訳編集後の検証状態

### 15.4 手動確認

実際の対象サイトでは次を確認する。

- 翻訳者、編集者、未ログイン利用者の表示差
- 単数形と複数形の編集
- Approve、Reject、Fuzzy、保存の既存挙動
- 動的ページ更新後の重複 UI
- ライトモード、ダークモード、キーボード操作
- Chrome と Firefox のパッケージ動作

## 16. 変更時のルール

### 16.1 新しいページ機能

1. 責務に対応する既存ファイルへ追加する
2. 独立性が高い場合だけ新しい `polykit-*.js` を作る
3. `jsScripts` の依存位置を決める
4. `web_accessible_resources` へ登録する
5. 初期化を `js/polykit.js` から呼ぶ
6. 設定、辞書、CSS、テストを必要に応じて追加する

### 16.2 新しい設定

1. 一意の `polykit_` 接頭辞付きキーを決める
2. 既定値と値の型を定義する
3. 設定画面のラベルと説明を辞書へ追加する
4. 破損値と旧形式からの移行方法を定義する
5. ポップアップと共有する場合は `chrome.storage.local` を正本にする

### 16.3 新しい検証ルール

1. 言語非依存か日本語固有かを分類する
2. DOM 非依存の判定関数として実装する
3. `warning`、`notice`、`off` の既定重要度を決める
4. 入力中、保存前、全件レビューの各経路を確認する
5. 正常例、異常例、境界例をテストする

## 17. 既知の制約

- GlotPress の DOM 構造とグローバル JavaScript API に依存する
- ページスクリプトは共有グローバル名前空間を使用する
- ページ設定の多くは WordPress.org オリジンの `localStorage` に保存される
- DOM 文字列置換による画面翻訳は、GlotPress 側の文言変更に追随する必要がある
- 実ブラウザーを使う End-to-End テストは現在のテスト構成に含まれない

GlotPress の更新で機能が壊れた場合は、DOM セレクターだけでなく、
既存イベント、権限情報、編集 API の変更も確認する。

## 18. 完了条件

全体設計に関わる変更は、次を満たした時点で完了とする。

- 対象ページの主要な翻訳・レビュー操作を妨げない
- 機能が利用者権限に従って表示・動作する
- 設定の既定値、保存先、移行方法が明確である
- 補助データ取得失敗時も編集を継続できる
- Chrome と Firefox の成果物を生成できる
- 追加または変更したロジックを自動テストで検証している
- 本書と機能別設計書が実装と一致している
